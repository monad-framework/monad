# CR-0001 — Assimilate selected AI-SDLC capabilities into Monad EOS

**State:** APPROVED

## Target

ADR-0006

## Summary

Assimilate selected AI-SDLC capabilities into Monad EOS through a staged Monad-native program that preserves EOS sovereignty, one canonical operational state, explicit authority, bounded execution, and continuity of the existing MVP product program.

## Motivation

The repository already contains most of the semantic and governance primitives needed for dependable AI-assisted engineering: canonical artifacts, authority levels, provenance, typed relationships, planning, policy gates, traceability, isolated execution, evidence, review, and canonical-state transactions. AI-SDLC contributes complementary patterns—especially deterministic Definition-of-Ready evaluation, decision routing, harness independence, bounded orchestration, proof-of-execution, emergent-work capture, exploration semantics, operator surfaces, and conformance—that can materially strengthen EOS if they are assimilated without creating a second control plane.

The change is therefore architectural composition rather than framework embedding. The aim is to make EOS progressively more capable while preserving Monad's existing authority and product-runtime decisions.

## Proposed Change

Adopt ADR-0006's selective-assimilation architecture and execute the program defined by `engineering/eos/AI-SDLC-ASSIMILATION-PROGRAM.md` as a sequence of separately authorized EOS evolution tranches.

The first tranche is EOS 0.9 — Decision & Readiness Engine. It will:

1. correct Decision lifecycle semantics so unresolved decisions can exist without a fabricated outcome;
2. define operational Decision, Approval, and Dependency handling through canonical-state transactions;
3. strengthen Work Packet readiness from state-plus-completeness into deterministic, explainable checks for unresolved markers, governing-reference validity, dependency closure, decision closure, authority, staleness, bounded scope, acceptance-testability, and verification expectations;
4. preserve deterministic-first evaluation, using semantic/model-assisted evaluation only when explicitly declared and only as non-sovereign evidence;
5. ensure a blocking decision or dependency prevents only affected work from progressing;
6. add operator-facing explanations for why a packet is or is not ready;
7. migrate canonical state and generated projections through an explicit schema/state-model evolution rather than hand edits.

Later tranches may add harness abstraction, independent review, dispatch frontier/worker pooling, failure recovery, proof of execution, emergent-work capture, exploration profiles, operator UI, conformance, advanced governance, and an optional AI-SDLC compatibility adapter. Each later tranche remains separately gated.

This ChangeRequest does not authorize copying AI-SDLC code, replacing Monad Work Packets with external task objects, adding a parallel `.ai-sdlc/` control store, changing the Rust MVP topology, or modifying product implementation scope.

## Alternatives

### Alternative A — Embed AI-SDLC directly

Rejected for this program. It would accelerate access to existing functionality but introduce overlapping lifecycle, task, dependency, policy, execution, and evidence concepts and increase coupling/licensing complexity.

### Alternative B — Selective Monad-native assimilation

Recommended. It preserves existing canonical authority, lets Monad use its semantic graph and provenance model as stronger inputs, and keeps future external-framework compatibility replaceable.

### Alternative C — Defer assimilation and continue current EOS evolution independently

Viable but inferior. It avoids near-term change but leaves known readiness/decision/orchestration gaps to be rediscovered piecemeal and risks later incompatibility between independently evolved mechanisms.

### Alternative D — Build the AI-SDLC compatibility bridge first

Rejected for sequencing. A bridge before Monad-native semantics stabilize would freeze an external conceptual model into the core and make the adapter a de facto authority boundary.

## Risks

1. **Control-plane overreach.** EOS evolution could grow into product architecture. Mitigation: preserve explicit product/EOS boundaries and Work Packet scopes.
2. **Canonical-state migration failure.** Adding operational kinds can create projection drift or inconsistent event history. Mitigation: version schemas/state model, use transaction-only migration, add rollback fixtures, and fail closed.
3. **Over-gating.** Stronger readiness may block useful exploratory work. Mitigation: later introduce explicit exploration/investigation readiness profiles rather than weakening delivery readiness.
4. **False semantic certainty.** Model-assisted readiness checks could be mistaken for authority. Mitigation: deterministic-first policy, explicit evidence provenance, and no silent authority elevation.
5. **Decision fatigue.** Surfacing every uncertainty could overwhelm the operator. Mitigation: classify/rank decisions, auto-resolve only pre-authorized low-risk mechanical cases, and block only affected work.
6. **Autonomy escalation.** Orchestration capabilities may exceed demonstrated safeguards. Mitigation: defer dispatch expansion until readiness, harness provenance, verification, and independent review are operational.
7. **External coupling.** Direct reuse could tie Monad to AI-SDLC implementation details. Mitigation: conceptual assimilation first; adapter later.
8. **License/provenance error.** Directly copied material may carry obligations. Mitigation: independent implementation by default and explicit provenance/license review for any reuse.
9. **MVP disruption.** EOS changes could invalidate active product work. Mitigation: parallel program streams; no retroactive rewriting of historical contracts/evidence.

## Migration / Rollback

Migration must be incremental and reversible at each tranche.

For EOS 0.9:

1. establish accepted architecture/design authority before implementation;
2. add versioned schemas and lifecycle definitions;
3. extend canonical-state schema/model and transaction support;
4. migrate a copy/fixture of current state and prove rollback/failure behavior;
5. add projections and CLI operations for new entity kinds;
6. add readiness predicates and explainability;
7. validate positive/negative fixtures;
8. verify existing lifecycle compatibility;
9. enable the strengthened gate only after migration verification passes.

Rollback before merge is ordinary branch rollback. After merge but before operational adoption, revert the EOS 0.9 implementation as a governed change. After canonical state has been migrated or new DEC/APR/DEP records exist, rollback must preserve recorded history and use a governed forward migration or feature disablement rather than deleting history.
