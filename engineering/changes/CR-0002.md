# CR-0002 — Expand Monad capability and roadmap baseline

**Status:** APPROVED  
**Date:** 2026-08-26  
**Authority:** Project Authority  
**Change class:** Product / requirements / architecture / roadmap expansion

## Summary

Expand Monad beyond the existing MVP semantic-kernel roadmap to include governed workspace intelligence, progressive multi-agent autonomy, automation/integrations, cryptographic attestations and identity, policy/change-control/audit, observability/analytics, deployment/portability, MCP/LSP/plugin/storage ecosystem surfaces, and measured parallel-performance/scale capabilities.

## Intent

The change extends Monad from a deterministic Engineering Knowledge Compilation Platform into a broader living engineering operating system while preserving the semantic graph, canonical artifacts, deterministic core, local-first operation, bounded authority, and evidence model as the foundation.

## Scope

This change authorizes planning and canonical-baseline updates for:

- workspace intelligence scoring and maturity tiers;
- unified memory–intelligence–execution learning loops;
- anti-hallucination memory, graph health, decay/staleness indicators, multi-vector memory, and semantic/result-aware caching;
- autonomous dependency-aware agent orchestration, progressive autonomy, operator decision stewardship, cross-harness review, provider routing, and resilience controls;
- resource/adapter models, intelligent automation, broad external integrations, and verified PR automation;
- DSSE-compatible attestations, cryptographic agility, post-quantum profiles, multi-party trust, key rotation, RBAC/passkeys, prompt-injection defense, secret masking, and capability sandboxing;
- declarative policy, readiness/done gates, formal change control, restore/rollback, and tamper-evident audit;
- OpenTelemetry, health dashboards, execution records/analytics, and optional privacy-governed hosted analytics;
- shared deployment/custom domains, workspace cloning/restoration, air-gapped/on-prem/multi-cloud operation, Docker/Nix profiles, and governed file/media handling;
- MCP, LSP/IDE, plugin SDK/registry/packs, pluggable graph/vector storage, and optional external runtime compatibility profiles;
- deterministic parallel execution plus declared throughput and local state-finalization benchmark targets.

## Scope protection

1. `MVP-RELEASE-1.md` remains the governing MVP scope contract.
2. New capabilities do not enter MVP solely because they are now planned.
3. Existing active execution under `PI-MVP-001` / `WC-MVP-0002` continues unless a separately governed blocker changes the critical path.
4. Post-MVP implementation requires ordinary ADR/specification/Ready/Authorize/Start gates.
5. Out-of-domain terminology is normalized to Monad-specific engineering semantics; optional external-runtime compatibility remains adapter-scoped.
6. Source/reference attributions from the originating feature list are intentionally excluded from repository artifacts.

## Required canonical updates

- expand `product/capabilities.md`;
- expand `product/product-requirements.md`;
- expand `product/constraints.md`;
- expand `architecture/quality-attributes.md` and architecture evolution boundaries;
- add a canonical expanded backlog and post-MVP Work Cycle/Sprint schedule;
- define post-MVP Product Goals, Program Increments, milestones, Features, Work Packets, and Stories;
- preserve rolling-wave task refinement rather than inventing implementation tasks before contracts are stable.

## Acceptance

This planning change is accepted when:

- all requested capability/requirement intent has a canonical disposition;
- no source attribution from the input list is committed;
- existing MVP work remains traceable and unambiguously sequenced before the expansion;
- every net-new Feature maps to a forecast Work Packet and Work Cycle/Sprint;
- post-MVP Product Goals/Increments/milestones are explicit;
- performance, security, cryptographic, privacy, provider, and deployment constraints are stated without weakening deterministic/local-first core principles;
- the resulting roadmap can be projected to GitHub Issues/Projects without inventing a second authority.
