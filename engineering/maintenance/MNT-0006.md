# MNT-0006 — EOS canonical transaction failure leaves rejected projection and event mutations

**State:** PLANNED

## Type

bug

## Summary

EOS canonical transactions are fail-closed with respect to advancement of `.eos/state/current.json`, but they are not currently atomic with respect to mutations made by the selected EOS runtime before canonical post-validation.

A command whose runtime returns success can mutate event history and compatibility projections, then fail canonical capture and leave those rejected mutations in the working tree.

## Observed Failure

The defect was demonstrated during:

```text
./scripts/eos maintain plan MNT-0005
```

The command performed the intended legacy/runtime mutation:

```text
MNT-0005
OPEN -> PLANNED
```

and changed:

* `.eos/maintenance.tsv`;
* `.eos/events.jsonl`;
* the visible lifecycle state in `engineering/maintenance/MNT-0005.md`.

Because malformed Markdown frontmatter prevented the frontmatter lifecycle projection from changing, canonical post-validation observed:

```text
TSV=PLANNED
frontmatter=OPEN
```

and correctly refused to advance canonical state.

However, after refusal:

* canonical MNT-0005 state remained `OPEN`;
* TSV state remained `PLANNED`;
* event history contained the rejected `OPEN -> PLANNED` event;
* Markdown visible state remained `PLANNED`;
* the canonical transaction receipt remained present.

The repository therefore entered explicit projection drift despite the canonical transaction having been rejected.

## Governing Invariant

A rejected EOS canonical transaction MUST have no authoritative or projected effect equivalent to a committed successful mutation.

The required invariant is:

> **Either the entire EOS mutation is captured as one consistent canonical transaction, or all transaction-local mutations are automatically returned to their exact pre-transaction state.**

This applies to:

* canonical state;
* lifecycle registries;
* append-only event history;
* Markdown lifecycle metadata;
* generated projections;
* transaction-local generated artifacts;
* other mutation surfaces governed by the canonical transaction.

## Current Architecture

The wrapper currently performs:

```text
canonical pre
    ↓
selected runtime mutates live repository projections
    ↓
runtime returns success
    ↓
canonical post validates/captures
```

This creates a vulnerability window:

```text
runtime mutation succeeds
    +
canonical post fails
    =
partial rejected transaction remains on disk
```

Failing to advance canonical state is correct but insufficient.

## Risk

If deferred, a failed EOS command may leave:

* lifecycle TSV drift;
* event-history drift;
* Markdown-state drift;
* orphaned newly created lifecycle artifacts;
* generated artifact drift;
* stale transaction receipts;
* misleading Git diffs;
* human confusion regarding whether an action actually occurred.

More importantly, operators may respond by manually repairing individual projections and accidentally:

* lose legitimate event history;
* retain rejected events;
* overwrite canonical state;
* create duplicate lifecycle operations;
* commit inconsistent history.

This is especially significant because EOS is the control plane for AI-driven engineering.

An AI executor must not be able to leave partial governance mutations merely because canonical validation catches an error late.

## Scope

At minimum inspect:

```text

tools/eos/eos.py

```

Additional mutation surfaces discovered during implementation are in scope only where they participate in canonical EOS transactions.

## Required Semantics

### Atomic outcome

An EOS mutation transaction MUST have exactly one of two terminal outcomes:

```text
COMMITTED
```

or:

```text
ROLLED_BACK
```

A failed transaction MUST NOT leave a third state equivalent to:

```text
CANONICAL_REJECTED_BUT_PROJECTIONS_MUTATED
```

### Pre-transaction identity

The transaction mechanism MUST retain sufficient information to prove and restore the exact pre-transaction state of every mutation surface it allows the selected runtime to change.

### Event history

Events produced by a transaction MUST not become durable accepted EOS history unless the corresponding transaction commits.

A rejected transaction MUST NOT require unsafe manual deletion of event history.

### Newly created entities

If a rejected transaction created a new lifecycle entity, rollback MUST prevent it from remaining as an unmanaged or apparently valid entity.

The implementation must define safe treatment for transaction-local:

* Markdown artifacts;
* registry rows;
* events;
* generated contracts;
* projection metadata.

### Existing entities

If a rejected transaction modified an existing entity, rollback MUST return lifecycle projections to the exact pre-transaction values.

### User-authored unrelated changes

Rollback MUST NOT erase unrelated pre-existing working-tree changes.

Therefore a blanket:

```text
git reset --hard
```

or equivalent repository-wide destructive rollback is forbidden.

## Preferred Architectural Direction

The preferred long-term model is transactional staging rather than mutation-then-repair.

Conceptually:

```text
canonical pre
    ↓
create isolated transaction staging area
    ↓
runtime writes proposed mutations to staging
    ↓
validate complete staged mutation
    ↓
atomically publish canonical state + projections + accepted events
```

This prevents rejected events and projections from becoming live in the first place.

If immediate full staging is disproportionate, an interim rollback implementation MAY be used only if it is:

* deterministic;
* exact;
* transaction-scoped;
* safe in a dirty working tree;
* able to distinguish transaction-created changes from pre-existing changes;
* tested against lifecycle creation and transitions;
* unable to erase unrelated user work.

## Transaction Receipt

The existing transaction receipt already records useful pre-transaction information, including:

* canonical revision;
* canonical digest;
* command;
* pre-command event count.

The repair MAY extend this receipt with additional transaction-scoped restoration metadata.

The receipt MUST remain insufficient by itself to authorize canonical advancement.

## Recovery Behavior

If canonical post-validation fails, EOS SHOULD:

1. identify the transaction being rejected;
2. restore transaction-owned mutation surfaces to their pre-transaction state;
3. retain diagnostic information explaining the rejection;
4. remove or terminally disposition the active transaction receipt;
5. verify canonical/projection consistency after rollback;
6. exit non-zero.

If automatic rollback itself fails, EOS MUST fail closed and provide an explicit recovery artifact/instruction without pretending consistency.

## Required Tests

### Existing lifecycle transition

Force post-validation failure after an existing entity transition.

Verify:

```text
canonical before == canonical after
TSV before == TSV after
Markdown lifecycle before == Markdown lifecycle after
event ledger before == event ledger after
```

for transaction-owned mutations.

### Entity creation

Force post-validation failure after `maintain create`, `create-wp`, or an equivalent entity creation.

Verify no rejected entity remains represented as committed lifecycle state.

### Dirty working tree

Begin with unrelated modified files.

Force transaction failure.

Verify unrelated modifications remain byte-identical.

### Event rollback

Verify transaction-local rejected events do not remain in the accepted event ledger.

### Transaction receipt

Verify successful rollback does not leave an active interrupted-transaction receipt.

### Rollback failure

Simulate a failure while restoring one transaction surface.

Verify EOS reports inconsistent/recovery-required state and never reports transaction success.

### Successful transaction

Verify ordinary successful transactions remain behaviorally unchanged.

### Determinism

Given identical pre-state and failed command behavior, rollback produces identical repository-governance state.

## Relationship to MNT-0003

MNT-0003 concerns loss of legitimate committed event history during Git merge/reconciliation.

MNT-0006 concerns retention of rejected transaction-local event history following failed canonical capture.

The two defects are distinct but jointly demonstrate that event-ledger integrity requires explicit transactional semantics.

## Relationship to MNT-0005

MNT-0005 exposed MNT-0006 but does not depend on MNT-0006 for its semantic identity resolution.

MNT-0005 implementation may proceed only after its own authority gate.

MNT-0006 should be resolved before materially increasing automated EOS mutation autonomy because failed automated governance mutations must be safely recoverable.
