# MNT-0001 — EOSV evidence freshness is not commit-stable

**State:** VERIFYING

## Type

bug

## Summary

EOSV evidence freshness is not commit-stable

## Context

GitHub issue #180; blocks WP-MVP-0001 EOSV verification

## Affected Artifacts / Components

- `tools/eos/verification_v2.py`: `source_fingerprint()` currently applies
  `workspace_hash(cwd, baseline)` and the raw `git_head(cwd)` baseline to
  ordinary WP validation as well as EOSE execution validation.
- EOSV evidence freshness checks, whose source hash is persisted in evidence
  records and compared during verification.
- Control-plane and generated artifacts under `.eos/`, `machine/`,
  `engineering/evidence/`, and `engineering/reviews/`, which must not stale
  ordinary WP evidence.

## Risk if Deferred

An `IN_PROGRESS` to `VERIFYING` transition, machine-document synchronization,
or committing EOSV evidence can change the current commit or working-tree diff
without changing verified source. EOSV then marks otherwise valid non-execution
evidence stale, blocking verification and encouraging unnecessary reruns. The
same instability makes freshness dependent on repository lifecycle mechanics
rather than the source and governing content actually evaluated.

## Proposed Resolution

Keep execution-bound evidence on its existing EOSE immutable-baseline and
baseline-diff fingerprint path. For non-execution WP evidence, replace the
current-HEAD/diff determinant with a deterministic content-addressed hash of
relevant tracked and untracked files. Sort canonical relative paths and hash
each path with semantic Markdown hashing (which ignores lifecycle `status`,
`updated`, and visible State/Status fields) or byte hashing for other files. Exclude
EOS control data, machine projections, evidence/review artifacts, and normal
VCS/build/cache directories. Continue including semantic hashes of governing
artifacts in the fingerprint payload.

## Validation

Run a focused regression script that creates a temporary Git fixture and
demonstrates that non-execution fingerprints remain stable across excluded
control/projection changes, lifecycle-only governing Markdown edits, and an
excluded-only commit with a new `HEAD`. The same script must demonstrate
changes for implementation source and semantic governing-content edits,
determinism for identical states, and retained execution baseline/diff drift
detection. Also run the required compile, EOS synchronization, strict
verification, and diff checks.

## Closure Evidence

Closure requires the code change, the focused regression result, successful
EOS synchronization and strict verification results, and a review confirming
that execution-bound EOSE semantics are unchanged. Capture the validation
outputs as MNT-0001 evidence through the normal EOS workflow; this maintenance
record remains `IN_PROGRESS` until the authorized lifecycle owner advances it.
