# MNT-0003 — EOS event ledger is not merge-safe across divergent append histories

**State:** PLANNED

## Type

bug

## Summary

The EOS event ledger is append-only within one working history but is not
currently protected against event loss when two Git histories diverge and are
later merged, synchronized, or reconciled.

A previously observed merge preserved current canonical state and registry
state while removing previously committed CR-0003 events from
`.eos/events.jsonl`.

The missing events had to be recovered from Git history.

## Origin Incident

The observed loss affected previously committed CR-0003 events including:

- `ENTITY_CREATED`;
- `STATE_TRANSITION`;
- `DECISION_RECORDED`.

The current-state projection survived, so ordinary current-state comparison did
not by itself prove that mutation history remained complete.

This demonstrates that:

```text
current state consistency

does not imply:

historical ledger completeness
Governing Invariant


A merge, synchronization, or reconciliation operation MUST NOT silently
remove a previously recorded valid EOS event.

More formally, for a resulting history R with immediate parent histories
P1...Pn:

events(P1) ∪ ... ∪ events(Pn) ⊆ events(R)

with equality of event identity and immutable event content for every inherited
event.

A result that cannot satisfy this condition MUST fail closed.

## Distinction from MNT-0006

MNT-0006 governs transaction-local atomicity:

one attempted local canonical transaction
    -> COMMITTED
       or
    -> ROLLED_BACK

MNT-0003 governs already-valid divergent histories:

history A
        \
         merge / synchronization
        /
history B

MNT-0006 prevents a rejected transaction from leaving partial mutations.

MNT-0003 prevents a later Git/history operation from silently deleting valid
mutations that were already committed.

The two invariants are independent.

## Current Architecture

.eos/events.jsonl is the EOS append-only mutation-history ledger.

.eos/state/current.json remains the sole canonical current operational state.

TSV and Markdown lifecycle representations remain projections.

Git remains the version-history and integrity ledger.

The event ledger is therefore historical evidence and reconstruction input, but
not a competing current-state authority.

## Root Cause

The repository currently treats .eos/events.jsonl as ordinary text for Git
merge purposes.

There is no repository-level append-union merge policy for the ledger.

Git's ordinary textual merge semantics do not express the EOS invariant that a
valid existing event may never disappear merely because two branches appended
different history.

EOS also lacks a Git-parent completeness check proving that the surviving
ledger contains every event inherited from each parent history.

Current event/state reconciliation can detect disagreement between a surviving
event ledger and other projections, but it cannot prove that an event absent
from the surviving ledger previously existed in another parent history.

## Required Properties

The repair MUST provide:

no silent event loss across ordinary Git merges;
immutable event identity;
exact inherited-event preservation;
deterministic validation;
fail-closed handling of conflicting duplicate event IDs;
fail-closed handling of incompatible concurrent lifecycle histories;
compatibility with the existing JSONL ledger;
preservation of existing canonical-state semantics;
no dependence on a developer-specific Git configuration;
deterministic regression coverage reproducing the original failure class.
## Non-Goals

This maintenance item does NOT:

replace Git;
replace .eos/events.jsonl with a database;
introduce distributed consensus;
solve multi-writer distributed transactions;
solve external API atomicity;

change authority semantics;
automatically resolve genuinely conflicting lifecycle decisions;
permit historical event deletion as conflict resolution.
## Proposed Resolution
### 1. Repository-native Git union behavior

Add to .gitattributes:

.eos/events.jsonl merge=union

Git's built-in union merge behavior requires no custom local merge-driver
configuration.

For ordinary divergent append histories, Git should therefore preserve additions
from both sides rather than selecting one append tail.

This mechanism is a convenience and first-line loss-prevention control.

It is NOT sufficient by itself to establish EOS semantic validity.

### 2. Central event-ledger semantics

Introduce a focused shared event-ledger utility, expected at:

tools/eos/event_ledger.py

It SHOULD provide deterministic functions equivalent to:

read_event_ledger(...)
event_map(...)
validate_event_identity(...)
validate_parent_superset(...)
validate_divergent_history(...)

The utility MUST treat event_id as immutable event identity.

### 3. Event identity integrity

Every event MUST have one event_id.

Within one resulting ledger:

event_id -> exactly one immutable event payload

is required.

If the same event_id appears with differing content, validation MUST fail.

The repair MUST NOT silently choose one payload.

### 4. Parent-history preservation

For a committed result:

result_commit
├── parent_1
└── parent_2

every event in every immediate parent ledger MUST remain present in the result.

For an ordinary single-parent commit, the same rule prevents historical event
deletion:

events(parent) ⊆ events(result)

For a merge commit:

events(parent_1) ∪ events(parent_2) ⊆ events(result)

The comparison MUST use event identity plus immutable event content rather than
line position alone.

### 5. Working-tree merge validation

During an uncommitted Git merge, when MERGE_HEAD is present, EOS SHOULD be
able to validate the working ledger against both:

HEAD
MERGE_HEAD

before the merge commit is accepted.

This allows loss to be detected before it becomes durable.

### 6. Divergent lifecycle conflict detection

Preserving every event does not imply that every union is semantically valid.

EOS MUST distinguish:

safe divergent append

from:

conflicting lifecycle history

Example safe case:

branch A:
WP-0001 event

branch B:
MNT-0003 event

Both may be retained.

Example conflicting case:

base:
WP-0001 DRAFT

branch A:
WP-0001 DRAFT -> READY

branch B:
WP-0001 DRAFT -> BLOCKED

Both events must be preserved for audit integrity, but EOS MUST NOT silently
declare one ordering authoritative.

Where both parent histories introduce distinct lifecycle-mutating events for the
same (entity_kind, target) after their common merge base, semantic merge
validation MUST fail closed unless the histories are provably identical or
otherwise already causally incorporated.

Resolution of such a conflict requires explicit governed reconciliation.

### 7. Event ordering

Ledger validation MUST NOT depend on arbitrary cross-entity line ordering.

Ordering of independent events from divergent histories may be deterministic,
but it must not manufacture causal semantics.

Per-entity lifecycle causality remains governed by the actual event fields and
canonical state.

### 8. Canonical-state relationship

The repair MUST preserve:

.eos/state/current.json

as the sole canonical current operational state.

The event ledger remains:

APPEND_ONLY_MUTATION_HISTORY

It does not become a second current-state authority.

### 9. Reconciliation integration

Canonical reconciliation MUST fail closed if:

a required parent event is missing;
a parent event's immutable content has changed;
duplicate event identity conflicts exist;
divergent lifecycle histories for one entity require explicit resolution.

Reconciliation MUST NOT "repair" these conditions by deleting one history.

### 10. Verification integration

./scripts/eos verify SHOULD include event-ledger integrity validation.

At minimum verification must be capable of proving:

CURRENT_LEDGER_PRESERVES_PARENT_HISTORY

for the applicable Git state.
