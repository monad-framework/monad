# MNT-0005 — EOS canonical REQ/SPEC identity model excludes repository-native requirement and specification identifiers

**State:** PLANNED
## Type

bug

## Summary

The EOS canonical Requirement and Specification identity model recognizes only
`REQ-*` and `SPEC-*` identifiers while the governed human-authored repository
already uses stable requirement and specification family identifiers outside
those prefixes.

As a result, valid governed artifacts are semantically present in the repository
but are incompletely represented by EOS machine traceability.

## Origin

This defect was identified as:

**AIENG-TRC-001 — Requirement/specification identifier namespace mismatch**

during the AIENG normative traceability and conformance review.

The AIENG normative specification baseline was subsequently approved while
explicitly preserving this finding as an unresolved pre-implementation
traceability obligation.

## Governing Constraints

The resolution MUST preserve:

* ADR-0003 stable governed document identity;
* ADR-0006 EOS sovereignty;
* ADR-0008 AI-driven engineering architecture;
* EOS-AI-0001;
* one canonical semantic identity per governed artifact;
* existing repository history;
* deterministic traceability;
* backwards compatibility for already-valid `REQ-*` and `SPEC-*` identifiers.

The resolution MUST NOT:

* silently renumber existing requirements;
* silently renumber existing specifications;
* create duplicate canonical identities for the same governed artifact;
* introduce an independent alias registry as a second identity authority;
* manufacture trace edges by manually editing `.eos/trace-edges.tsv`;
* weaken duplicate-ID detection;
* weaken stable-identity guarantees;
* broaden this maintenance item into unrelated EOS redesign.

## Current State

### Canonical Requirement model

The canonical Requirement schema currently requires:

```text
REQ-*
```

and the EOS domain model likewise declares the Requirement namespace using the
`REQ-*` form.

### Canonical Specification model

The canonical Specification schema currently requires:

```text
SPEC-*
```

and the EOS domain model likewise declares the Specification namespace using the
`SPEC-*` form.

### Existing requirement identifiers

The governed product requirements corpus uses stable identifiers including:

```text
FR-*
QR-*
```

These represent requirement classes, not informal labels.

### Existing specification identifiers

The governed specification corpus currently contains stable family identifiers
including:

```text
FUN-*
IFC-*
SEC-*
TECH-*
DATA-*
MKE-*
```

Examples include:

```text
FUN-AIENG-0001
IFC-AIENG-0001
SEC-AIENG-0001
TECH-HARNESS-0001
DATA-SOURCE-0001
MKE-CORE-0001
```

These identifiers are already part of repository history and governed
cross-references.

## Root Cause

EOS currently conflates two different concepts:

1. **entity type**, such as Requirement or Specification;
2. **literal identifier prefix**, such as `REQ` or `SPEC`.

The repository architecture has evolved toward typed identifier families in
which the prefix can also express a useful subtype.

For example:

```text
Requirement
├── FR-*     functional requirement
├── QR-*     quality requirement
└── REQ-*    generic requirement

Specification
├── FUN-*    functional specification
├── IFC-*    interface specification
├── SEC-*    security specification
├── TECH-*   technical specification
├── DATA-*   data specification
├── MKE-*    Monad Knowledge Engine specification
└── SPEC-*   generic specification
```

The entity type and identifier family are therefore related but not identical.

## Machine-Level Effects

The mismatch affects more than JSON Schema validation.

The legacy/current EOS trace implementation also contains prefix-specific
behavior for:

* identifier extraction;
* explicit relationship parsing;
* source/target classification;
* inferred edge types;
* requirement coverage;
* specification coverage;
* Work Packet-to-requirement/specification trace classification;
* impact classification.

Consequently, repository-native IDs such as `FR-043` and
`FUN-AIENG-0001` may appear in prose while remaining invisible to portions of
the canonical machine trace model.

## Risk if Deferred

If deferred:

1. semantic requirements/specifications remain underrepresented in machine
   traceability;
2. trace coverage can report misleading results;
3. AIENG requirement-to-specification coverage cannot be claimed as complete;
4. impact analysis may omit governed dependencies;
5. stale-dependency propagation may miss affected artifacts;
6. future implementation planning may consume incomplete governing context;
7. machine and human views of engineering identity continue to diverge.

Because AI-driven engineering depends heavily on compiled governed context,
leaving this mismatch unresolved would undermine one of the principal controls
the new operating model depends upon.

## Recommended Resolution

### Resolution principle

Treat established repository-native IDs as **first-class canonical identifiers
of their entity type**, not aliases for newly invented `REQ-*` or `SPEC-*`
identities.

The canonical entity type determines whether an artifact is a Requirement or
Specification.

The literal prefix may additionally encode a stable requirement/specification
family.

### Requirement identifier families

Requirement identity SHOULD accept at least:

```text
REQ-*
FR-*
QR-*
```

where:

* `REQ-*` remains the generic Requirement family;
* `FR-*` remains a functional-requirement family;
* `QR-*` remains a quality-requirement family.

### Specification identifier families

Specification identity SHOULD accept the currently established families:

```text
SPEC-*
FUN-*
IFC-*
SEC-*
TECH-*
DATA-*
MKE-*
```

where `SPEC-*` remains available as the generic Specification family.

Before implementation, the repository MUST be scanned deterministically for
any additional already-established specification family so that the repair does
not encode an incomplete hand-selected list.

### Domain-model representation

The canonical domain model SHOULD distinguish:

```text
entity_type
```

from:

```text
accepted identifier families
```

rather than implying that one entity type must always have one literal prefix.

The domain model MAY retain `REQ` and `SPEC` as generic/default prefixes, but it
SHOULD explicitly represent the accepted native prefixes or equivalent pattern.

### Core schema changes

Update:

```text
.eos/schemas/core/requirement.schema.json
.eos/schemas/core/specification.schema.json
```

so valid existing repository-native IDs conform without changing their
identity.

The schemas MUST continue rejecting unrelated malformed IDs.

### EOS identifier recognition

Update EOS identifier recognition so the central identifier matcher recognizes
the canonical native Requirement and Specification families.

The implementation SHOULD centralize classification with semantic predicates
equivalent to:

```text
is_requirement_id(id)
is_specification_id(id)
```

rather than scattering repeated `startswith("REQ-")` and
`startswith("SPEC-")` checks.

### Trace inference

Trace inference MUST treat:

```text
FR-*
QR-*
```

as Requirement entities and:

```text
FUN-*
IFC-*
SEC-*
TECH-*
DATA-*
MKE-*
SPEC-*
```

as Specification entities.

Existing semantic edge behavior must therefore apply consistently.

Examples:

```text
WP -> FR/QR
    implements

WP -> FUN/IFC/SEC/TECH/DATA/MKE/SPEC
    satisfies

Specification -> FR/QR
    satisfies

Specification -> ADR/QA
    constrained-by
```

Exact edge direction remains governed by the existing trace contract.

### Trace coverage

`./scripts/eos trace coverage` MUST count repository-native Requirement and
Specification entities rather than only `REQ-*` and `SPEC-*`.

The resulting coverage metric MUST represent the actual governed corpus.

### Artifact resolution

Any EOS artifact-ID lookup that relies on the legacy identifier matcher MUST
recognize the expanded canonical families.

### Staleness and impact analysis

Impact and stale-dependency logic MUST operate on native Requirement and
Specification identifiers exactly as it currently does for `REQ-*` and
`SPEC-*`.

### Generated trace state

`.eos/trace-edges.tsv` remains generated state.

The repair MUST rebuild it from canonical source artifacts.

No manual trace edges are authorized as part of the repair.

## Compatibility

The repair MUST be additive.

Existing:

```text
REQ-*
SPEC-*
```

identifiers remain valid.

The change does not redefine an existing stable artifact ID.

It expands the set of identifiers recognized for the existing Requirement and
Specification entity types.

## Identity Semantics

This maintenance resolution is consistent with ADR-0003.

ADR-0003 establishes that an explicit governed identifier is the stable
Document ID where the artifact contract defines one.

Therefore:

```text
FR-043
```

must remain `FR-043`, and:

```text
FUN-AIENG-0001
```

must remain `FUN-AIENG-0001`.

Creating a second canonical `REQ-*` or `SPEC-*` identity for either artifact
would introduce unnecessary duplicate identity and mapping complexity.
