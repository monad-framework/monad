## Release policy

1. Move user-visible entries from `Unreleased` into a dated release section.
2. Use `MAJOR.MINOR.PATCH` according to compatibility impact.
3. Link each entry to an issue, work packet, ADR, or pull request when one
   exists.
4. Describe effects and migration needs; do not merely restate commit titles.
5. Create and sign the matching Git tag only after release gates pass.

## Entry guidance

- **Added**: new capabilities or supported behaviors.
- **Changed**: backward-compatible changes to existing behavior.
- **Deprecated**: supported behavior scheduled for removal.
- **Removed**: deleted behavior or compatibility breaks.
- **Fixed**: corrected defects.
- **Security**: vulnerability fixes or meaningful control changes.
